---

## 1. 아키텍처 목표

- 교사 1명과 학생 최대 30명이 한 세션에 안정적으로 참여한다.
- 정답·힌트·진행 판정은 서버와 데이터베이스 경계 안에 둔다.
- 초안과 게시 버전을 분리해 수업 중 콘텐츠가 바뀌지 않게 한다.
- 개인전과 팀전의 진행 데이터를 분리한다.
- 방·문제·오브젝트·오디오는 데이터 기반으로 관리한다.
- 기능별 경계를 유지하되, 아직 필요하지 않은 추상화는 만들지 않는다.

---

## 2. 시스템 구성

```text
교사/학생 브라우저
        │ HTTPS / Realtime
        ▼
Next.js App Router
├─ 교사 화면 및 Server Actions
├─ 학생 플레이 화면
├─ Route Handlers
└─ 서버 전용 도메인 서비스
        │
        ▼
Supabase
├─ PostgreSQL + RLS
├─ Auth (교사)
├─ Realtime
└─ 관리자 등록 자산 메타데이터
```

Vercel은 Next.js 애플리케이션을 배포하고, Supabase는 인증·데이터베이스·실시간 이벤트를 담당한다.

---

## 3. 사용자와 인증 경계

### 3.1 교사

- Supabase Auth를 사용하는 인증 사용자다.
- 자기 게임·초안·세션만 생성하고 변경할 수 있다.
- 공개 콘텐츠는 읽고 자기 초안으로 복제할 수 있다.

### 3.2 학생

- 별도 회원가입 없이 세션 코드로 참여한다.
- 서버가 발급한 `studentSessionId`로 식별한다.
- 닉네임은 표시용이며 중복을 허용한다.
- 재접속은 `studentSessionId`를 이용해 복구한다.

---

## 4. 애플리케이션 경계

```text
src/
├─ app/
│  ├─ (teacher)/       교사 화면
│  ├─ (play)/          학생 플레이 화면
│  └─ api/             외부 입력을 받는 Route Handlers
├─ components/ui/      공용 표현 컴포넌트
├─ features/
│  ├─ builder/          게임 제작기
│  ├─ play/             학생 플레이 UI
│  ├─ session/          세션 및 모드별 흐름
│  └─ library/          공개·검색·복제
├─ lib/
│  ├─ constants/        확정 규칙 상수
│  ├─ supabase/         브라우저 클라이언트
│  └─ utils/            범용 유틸리티
├─ server/
│  ├─ auth/             소유권·권한 확인
│  ├─ grading/          정답 판정
│  ├─ progress/         출구·방 이동·완료 판정
│  └─ supabase/         서버 전용 클라이언트
└─ types/               공용 타입 및 생성된 DB 타입
```

- `src/server/`는 클라이언트에서 import할 수 없게 `server-only` 경계를 둔다.
- 기능 폴더는 실제 기능을 구현하는 Sprint에서 채운다. Sprint 1에서는 빈 폴더와 설명만 둘 수 있다.

---

## 5. 데이터 영역

세부 컬럼과 정책은 후속 DB 설계 문서에서 확정한다. 현재 구조적 경계는 다음과 같다.

### 5.1 제작 및 버전

- 게임 초안
- 초안의 방·오브젝트·문제·정답·힌트·오디오
- 게시 시 생성되는 불변 `game_versions` 스냅샷
- 공개 설정과 복제 이력

### 5.2 수업 세션

- 세션은 시작 시 `gameVersionId`를 고정 참조한다.
- 모드는 개인전 또는 팀전으로 생성 시 확정한다.
- 학생 참여자는 `studentSessionId`로 식별한다.

### 5.3 진행

- 개인전: `player_progress`
- 팀전: `team_progress`
- 시도·오답·힌트 해제는 모드와 관계없이 학생 개인 기준으로 기록한다.
- `teacher_overrides`는 정답 기록과 분리한다.

### 5.4 마스터 및 자산

- 학년·과목·문제 유형·등록 자산은 DB 마스터 데이터로 관리한다.
- 교사 업로드는 MVP에서 제공하지 않는다.

---

## 6. 정답 판정 흐름

```text
학생 답안 제출
→ 서버에서 세션·학생·문제 접근 권한 검증
→ 서버에서 정답 조회 및 판정
→ attempts 기록
→ 개인 힌트 해제 여부 계산
→ 개인 또는 팀 해결 상태 갱신
→ 출구·방 이동·탈출 가능 여부 계산
→ 정답 원문 없는 최소 결과 반환
```

학생용 응답과 HTML에 정답·정답 인덱스·잠긴 힌트를 포함하지 않는다. 미리보기도 같은 판정 경로를 사용한다.

---

## 7. 실시간 구조

Realtime은 다음 상태 전달에 사용한다.

- 학생 입장·이탈·재접속
- 학생 또는 팀의 현재 방과 해결 수
- 도움 요청과 교사 확인 완료
- 세션 시작·종료 상태

정답 자체나 정답 판정 기준은 Realtime payload로 보내지 않는다. 서버와 DB가 진실의 원천이며, Realtime은 이미 기록된 상태를 UI에 반영하는 수단이다.

---

## 8. 초안·게시·복제 흐름

```text
초안 자동 저장
→ 게시 검증
→ 불변 스냅샷 생성
→ 세션이 해당 버전 ID 고정 참조

공개 게임 검색
→ 미리보기
→ 복제
→ 소유자가 다른 새 초안 생성
```

게시 버전을 직접 수정하거나 삭제하는 애플리케이션 경로를 만들지 않는다.

---

## 9. 보안 원칙

- 모든 테이블에 RLS를 적용한다.
- `service_role`은 클라이언트와 `NEXT_PUBLIC_*`에 넣지 않는다.
- 교사 소유권은 서버에서 확인한다.
- 학생은 자기 세션 또는 허용된 팀 진행 정보만 접근한다.
- 정답·힌트 원문은 학생 역할에서 직접 조회할 수 없다.
- 서버 판정 함수는 클라이언트 공유 모듈에 두지 않는다.

---

## 10. 테스트 경계

- Vitest: 규칙·판정·좌표·게시 검증·팀 배정 같은 순수 로직
- Playwright: 제작→게시, 입장→플레이→탈출, 재접속, 도움 요청, 팀전
- RLS와 소유권: 통합 테스트에서 타인 데이터 접근 차단 확인
- 보안 회귀: 학생 API·HTML·미리보기에 정답이 없는지 확인

---

## 11. 아직 확정하지 않는 것

Sprint 1에서는 다음을 설계하거나 구현하지 않는다.

- 최종 DB 컬럼과 인덱스
- 상세 API 계약
- 자유 배치 상태 관리 방식
- UI 컴포넌트 라이브러리
- 캐시·큐·별도 백엔드 서비스
- 대규모 추상화 또는 플러그인 구조

필요한 Sprint에서 별도 설계 문서를 작성하고 사용자 승인을 받은 뒤 확정한다.
