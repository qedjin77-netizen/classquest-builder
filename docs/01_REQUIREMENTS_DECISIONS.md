## 1. 오늘 확정한 결정

### D-01. 모든 문제는 필수 문제다

**결정**

- MVP에서 **모든 문제가 필수 문제**다.
- **보너스 문제와 선택 문제는 지원하지 않는다.**
- 방마다 **필수 문제 3~5개**를 둔다.

**이유**

- 초기 검토에서 "필수 문제를 모두 정답 처리하면 다음 방으로 이동"이라는 규칙과 "방마다 문제 3~5개"라는 규칙이 충돌했다. 전부 필수라면 "필수"라는 수식이 불필요하고, 일부만 필수라면 나머지 문제의 성격이 정의되지 않았다.
- 초등 3~6학년 수업에서는 **"이건 안 풀어도 돼"가 학생에게 혼란**을 준다. 어떤 문제를 풀어야 하는지 판단하는 부담을 아이에게 넘기지 않는다.
- 교사도 준비 시간이 짧다. 문제마다 필수/선택을 결정하는 단계는 제작 시간을 늘린다.
- 방당 3~5개는 그 자체로 이미 적은 수다. 그 안에서 다시 선택 문제를 나눌 실익이 없다.

**구현 영향**

- `questions`에 필수 여부 컬럼을 만들지 않는다.
- 게시 검증은 "방당 문제 3~5개"만 확인한다. "필수 문제 N개 이상" 검사는 없다.
- 출구 개방 조건은 "그 방의 문제 개수 = 해결한 문제 개수"로 단순해진다.

### D-02. 방 안은 자유 탐색, 방 사이는 순차 진행

**결정**

- 방 **안에서는 문제 오브젝트를 자유롭게 탐색**한다. 풀이 순서를 강제하지 않는다.
- 방과 방 사이는 **1번 방 → 2번 방 → 3번 방 순차 진행**이다.
- **현재 방의 모든 필수 문제를 정답 처리해야 다음 방 출구가 열린다.**

**이유**

- "자유 탐색"과 "모든 필수 문제 정답 시 다음 방 이동"이 어느 범위에 적용되는지 모호했다. 자유 탐색을 방 사이에까지 적용하면 방 이동 조건 자체가 무의미해진다.
- 방탈출이라는 장르의 기본 형태가 **"한 방을 다 풀어야 다음 방"**이다. 이 구조를 깨면 게임의 목표 감각이 사라진다.
- 반대로 방 안에서까지 순서를 강제하면 탐색의 재미가 없어지고, 한 문제에서 막힌 학생이 아무것도 못 하게 된다.
- 방 내부 자유 + 방 사이 순차는 **탐색의 자유와 진행의 명확함을 동시에** 준다.

**구현 영향**

- 이전 방으로 되돌아가는 것은 허용한다. 건너뛰기는 허용하지 않는다.
- 출구 개방 판정은 서버가 한다. 클라이언트의 "다 풀었어요"를 신뢰하지 않는다.

### D-03. 팀전에서 해결 상태는 팀 공유, 오답·힌트는 개인 계산

**결정**

- **오답 횟수는 학생 개인별로 계산한다.**
- **같은 학생이 같은 문제를 2회 틀리면 그 학생에게만 힌트를 표시한다.**
- **팀원에게 힌트를 자동 공유하지 않는다.**
- **팀원이 문제를 해결하면 팀의 해당 문제는 해결 완료로 처리한다.**

**이유**

- 오답 횟수를 팀 합산으로 세면, **아직 문제를 한 번도 안 본 학생이 이미 열린 힌트를 보게 된다.** 스스로 생각할 기회를 빼앗긴다.
- 특히 4~6명 팀에서는 합산 2회가 순식간에 채워진다. 사실상 모든 문제에 힌트가 처음부터 열린 것과 같아진다.
- 반대로 해결 상태까지 개인별로 두면 팀전이 "같은 방에서 각자 하는 개인전"이 된다. 협력의 의미가 없다.
- 따라서 **협력이 필요한 축(해결 상태)은 공유하고, 개인의 학습 과정에 해당하는 축(오답·힌트)은 분리**한다.
- 팀이 이미 푼 문제라도 아직 안 푼 팀원은 계속 시도할 수 있게 둔다. 학습 기회를 닫지 않는다.

**구현 영향**

- `attempts`와 `hint_unlocks`는 팀전에서도 **학생 개인 기준**으로 기록한다.
- `team_progress`에 오답 횟수 컬럼을 만들지 않는다. 팀 진행 테이블은 해결한 문제와 현재 방만 가진다.

### D-04. 자동 저장은 초안에만, 게시는 불변 스냅샷

**결정**

- **자동 저장은 작성 중인 초안에만 적용한다.**
- **게시 시 불변 스냅샷 버전을 생성한다.**
- **게시된 버전은 직접 수정하지 않는다.**
- 게시 후 수정하면 **새로운 초안 또는 새 버전**을 만든다.
- **진행 중인 수업은 시작 당시 게시 버전을 계속 사용한다.**

**이유**

- "자동 저장"과 "게시 버전 불변"은 표면상 충돌한다. 자동 저장이 게시본에 닿으면 불변성이 깨진다. 저장 대상을 초안으로 한정해 해소했다.
- 교사가 수업 중에 다른 반 수업을 준비하며 게임을 고치는 상황이 실제로 발생한다. 이때 **진행 중인 수업의 화면이 갑자기 바뀌면 수업이 무너진다.**
- 문제나 정답이 플레이 도중 바뀌면 학생의 진행 기록과 실제 콘텐츠가 어긋나 채점 결과를 신뢰할 수 없게 된다.
- 공유된 게임을 다른 교사가 복제한 뒤 원본이 바뀌는 것도 막아야 한다.

**구현 영향**

- 세션은 버전 ID를 **고정 참조**한다. "최신 버전"을 조회하지 않는다.
- 스냅샷은 참조가 아니라 **실제 복사본**이어야 한다. 초안을 가리키는 참조만 저장하면 불변성이 깨진다.
- 마이그레이션으로 과거 게시 버전의 콘텐츠를 변경하지 않는다.

### D-05. 미리보기도 학생과 동일한 서버 판정, 정답은 편집 화면에서만

**결정**

- **미리보기에서도 학생 플레이와 동일한 서버 판정 방식을 사용한다.**
- **정답 원문을 브라우저 번들, HTML, 클라이언트 상태에 포함하지 않는다.**
- **교사용 문제 편집 화면에서만 권한을 확인한 뒤 정답을 볼 수 있다.**

**이유**

- "정답을 클라이언트에 노출하지 않는다"와 "공개 게임 미리보기"가 충돌할 소지가 있었다. 미리보기를 편의상 예외로 두면 그 경로가 곧 정답 유출 통로가 된다.
- 미리보기 URL은 **공개 콘텐츠 검색을 통해 누구나 접근**할 수 있다. 학생이 미리보기 화면으로 정답을 확인하는 우회로가 생긴다.
- 판정 경로가 둘로 갈라지면 두 경로의 동작이 시간이 지나며 달라진다. 하나로 유지하는 편이 안전하고 유지보수도 쉽다.
- 교사는 정답을 봐야 문제를 만들 수 있다. 다만 **자기 게임에 한해서**다. 공개된 남의 게임 정답까지 볼 이유는 없다.

**구현 영향**

- 미리보기 전용 채점 API를 만들지 않는다.
- 정답 조회는 소유 교사 확인을 거친 서버 경로에서만 가능하다.
- 서버 컴포넌트 직렬화 payload, `data-*` 속성, 소스맵도 점검 대상이다.
- 관련 테스트를 필수로 만든다. (`CLAUDE.md` 5.1)

### D-06. 막힌 학생은 도움 요청과 교사 확인 완료로 지원한다

**결정**

- **무제한 재도전**을 허용한다.
- **2회 오답 후 힌트**를 표시한다.
- 학생 화면에 **"교사에게 도움 요청" 버튼**을 제공한다.
- 교사 대시보드에서 해당 학생의 특정 문제를 **"교사 확인 완료"**로 처리할 수 있다.
- **교사의 강제 다음 방 이동 기능은 MVP에서 제외한다.**
- **교사 확인 완료 기록은 정답 기록과 구분해서 저장한다.**

**이유**

- 무제한 재도전과 힌트 1개만으로는 **끝내 못 푸는 학생이 수업 시간 내내 첫 방에 갇힌다.** 이탈 경로가 필요했다.
- 초기 검토에서는 교사의 강제 방 이동을 제안했으나, **방을 통째로 건너뛰면 그 방의 나머지 문제까지 학습 기회를 잃는다.** 문제 단위로 처리하는 편이 손실이 적다.
- 도움 요청 버튼은 교사가 30명을 동시에 지켜볼 수 없다는 현실을 반영한다. 학생이 직접 신호를 보내는 편이 빠르다.
- 교사 확인을 정답으로 기록하면 **성취 데이터가 오염된다.** 어떤 학생이 실제로 풀었고 어떤 학생이 도움을 받았는지 구분할 수 없게 되어 수업 개선에 쓸 수 없다.
- 분리 저장하면 "이 문제는 교사 확인이 많다 → 문제가 너무 어렵다"는 진단도 가능해진다.

**구현 영향**

- `help_requests`(도움 요청)와 `teacher_overrides`(교사 확인 완료)를 `attempts`와 별도 테이블로 둔다.
- 교사 확인은 **출구 개방 조건에는 반영**하되, **정답 통계에는 합산하지 않는다.**
- 강제 방 이동 API·UI를 만들지 않는다.

### D-07. 팀 수는 2~6팀, 정원은 균등 배정

**결정**

- **팀 수: 교사가 2~6팀 중 선택**한다.
- **팀 정원: 별도로 고정하지 않고 학생 수를 팀 수로 균등 배정**한다.

**이유**

- 학급 인원은 20명대에서 30명까지 편차가 크다. 정원을 고정하면 어떤 학급에서는 팀이 남거나 모자란다.
- 팀 수를 교사가 고르게 하면 **모둠 책상 배치에 맞춰** 운영할 수 있다. 교실 배치는 학교마다 다르다.
- 하한 2팀 — 1팀은 팀전의 의미가 없다.
- 상한 6팀 — 30명 기준 6팀이면 팀당 5명이다. 이보다 잘게 나누면 팀당 2~3명이 되어 개인전과 차이가 없어지고, 교사가 대시보드에서 추적할 대상도 늘어난다.
- 나누어떨어지지 않을 때는 앞 팀부터 1명씩 더 배정한다. 인원 차이는 최대 1명이다.

**구현 영향**

- 팀 정원 상수를 만들지 않는다. 배정 로직은 학생 수와 팀 수만 입력받는다.
- 교사는 자동 배정 결과를 수동으로 조정할 수 있다.

### D-08. 세션 시간 제한은 선택 기능, 기본값은 제한 없음

**결정**

- 시간 제한은 **선택 기능**이며 **기본값은 제한 없음**이다.

**이유**

- 40분 수업에 맞춰 시간을 쓰고 싶은 교사가 있는 반면, 학생마다 속도가 다른 것을 그대로 두려는 교사도 있다. 어느 쪽도 기본값으로 강제할 근거가 없다.
- 초등 저학년에 가까울수록 **시간 압박이 학습 불안**으로 이어진다. 기본값을 "제한 없음"으로 두는 편이 안전하다.
- 처음 써 보는 교사가 시간 설정 때문에 수업이 중간에 끊기는 사고를 겪지 않게 한다.

**구현 영향**

- 남은 시간 판정 기준은 **서버 시각**이다. 클라이언트 타이머는 표시용이다.
- 시간이 끝나면 세션을 종료하고 결과 화면으로 넘어간다. 남은 문제는 미해결로 기록한다.
- 시간 제한이 항상 켜져 있다고 가정하는 코드를 쓰지 않는다.

### D-09. 닉네임 중복은 허용하고 studentSessionId로 구분한다

**결정**

- **닉네임 중복은 허용한다.**
- 진행 상태는 내부 **`studentSessionId`**로 구분한다.

**이유**

- 한 학급에 같은 이름이 있는 경우가 실제로 흔하다. 중복을 막으면 **수업 시작 시점에 입장이 막히는 학생**이 생긴다. 30명이 동시에 들어오는 상황에서 이 지연은 크다.
- 이름 뒤에 번호를 붙이라고 안내하는 것도 초등 3학년에게는 부담이다.
- 닉네임을 키로 쓰면 재접속 복구 시 **다른 학생의 진행 상태를 잘못 이어받는** 사고가 난다. 실제 키를 서버 발급 식별자로 두면 이 위험이 사라진다.

**구현 영향**

- 닉네임으로 참여자를 조회·매칭하는 코드를 쓰지 않는다.
- 재접속은 `studentSessionId`로만 복구한다. 토큰이 사라진 경우(다른 기기, 저장소 삭제)에는 **교사가 대시보드에서 기존 참여자와 연결**해 준다. 닉네임 자동 매칭은 하지 않는다.
- 대시보드에서는 입장 순번 등 보조 정보를 함께 표시해 교사가 구분할 수 있게 한다.

### D-10. 힌트는 문제당 1개

**결정**

- 한 문제당 **힌트 1개**.

**이유**

- 다단계 힌트는 **교사의 제작 부담을 문제당 2~3배로 늘린다.** "20~30분 안에 게임 하나"라는 목표와 맞지 않는다.
- 단계별 해제 조건(몇 회 오답에 몇 번째 힌트)을 추가로 정해야 하고, 판정 로직과 테스트도 그만큼 늘어난다.
- 힌트로 부족한 학생을 위한 경로는 **D-06(도움 요청 → 교사 확인 완료)**이 이미 담당한다. 힌트를 겹겹이 쌓을 필요가 없다.

**구현 영향**

- 힌트를 배열이나 단계 구조로 만들지 않는다.
- 게시 검증에서 "모든 문제에 힌트 1개 존재"를 확인한다.

---

### D-11. 자산은 관리자·개발자가 등록한 것만 사용한다

**결정**

- **효과음과 BGM 파일은 관리자 또는 개발자가 등록한 자산에서만 선택**한다.
- **교사의 사용자 오브젝트 이미지 업로드는 MVP에서 제외**한다.

**이유**

- 업로드를 허용하면 **저작권 문제**가 곧바로 생긴다. 교사가 웹에서 받은 이미지·음원을 올리고, 그 게임이 공개 콘텐츠로 퍼지면 대응이 어렵다.
- **부적절한 이미지 업로드**에 대한 검수 수단이 MVP에는 없다. 초등학생이 보는 화면이라 위험이 크다.
- 업로드 기능 자체도 작지 않다. 스토리지 설정, 용량 제한, 파일 형식 검증, 이미지 최적화, 삭제 정책, 비용 관리가 따라온다. 3개월 안에 넣을 항목이 아니다.
- 큐레이션된 자산만 쓰면 **게임들의 시각적 완성도가 고르게** 유지되는 이점도 있다.

**구현 영향**

- MVP에는 **교사용 파일 업로드 기능이 없다.** 업로드 UI, 스토리지 버킷 쓰기 권한, 파일 검증 로직을 만들지 않는다.
- 자산 목록은 `audio_assets` · `image_assets` 테이블에 두고 **시드 스크립트**로 등록한다.
- 등록하는 파일은 **라이선스가 확인된 것만** 사용한다.

---

### D-12. 유료 거래는 제외하고 무료 공유만 지원한다

**결정**

- **유료 콘텐츠 거래는 제외**하고 **무료 공개·검색·미리보기·복제만 지원**한다.

**이유**

- 결제를 넣는 순간 정산, 세금, 환불, 분쟁 처리, 판매자 신원 확인이 따라온다. 이는 3개월 MVP의 범위를 넘는다.
- 공립학교 교사가 수업 자료를 판매하는 것에는 별도의 제도적 검토가 필요하다. 기술 결정만으로 진행할 사안이 아니다.
- MVP 단계에서 검증할 것은 **"교사들이 서로의 게임을 실제로 가져다 쓰는가"**다. 무료 공유만으로 이 질문에 답할 수 있다.

**구현 영향**

- 결제, 정산, 가격 책정, 크레딧 관련 기능·테이블·의존성을 만들지 않는다.

## 3. 추후 검토 항목

MVP 이후에 다시 볼 항목. **지금 구현하지 않는다.**

### 3.1 이번에 제외했으나 재검토 여지가 있는 것

| 항목 | 재검토 조건 |
| --- | --- |
| 선택 · 보너스 문제 | 빨리 끝낸 학생의 대기 시간이 실제로 문제가 되는지 확인한 뒤 |
| 다단계 힌트 | 힌트 1개로 부족하다는 신호(교사 확인 완료 비율)가 데이터로 확인되면 |
| 교사의 이미지 업로드 | 저작권 안내와 신고·검수 절차를 갖출 수 있을 때 |
| 유료 거래 | 무료 공유가 실제로 쓰인다는 것이 확인되고, 제도 검토가 끝난 뒤 |
| 방 개수 가변화 | 3개가 수업 시간에 맞지 않는다는 피드백이 모이면 |

### 3.2 아직 정하지 않은 것

| 항목 | 내용 |
| --- | --- |
| 단답형 정답 비교 규칙의 세부 | 공백·대소문자 정규화는 정했다. 유사어·띄어쓰기 변형·조사 차이를 어디까지 허용할지 미정. **AI 유사도 판정은 사용하지 않는다.** 복수 정답 문자열 등록으로 대응할지 검토 |
| 탈출 화면에 표시할 지표 | 소요 시간과 정답 수는 정했다. 순위 표시 여부는 미정. 초등에서 순위 노출의 교육적 영향 검토 필요 |
| 학습 결과 리포트 | 세션 종료 후 교사가 받을 요약 형태(문제별 정답률, 학생별 성취)와 내보내기 형식 |
| 게시 버전 보관 정책 | 버전을 무한히 쌓을지, 개수·기간 상한을 둘지 |
| 세션 데이터 보관 기간 | 학생 진행 기록을 얼마나 보관할지. 개인정보 최소 수집 원칙과 함께 검토 |
| 접근성 | 색약 대응, 키보드 조작, 화면 낭독기 지원 수준 |
| 저사양 기기 대응 | 학교 PC실 사양 기준과 이미지·오디오 용량 상한 |
| 동시 접속 부하 | 30명 × 다수 학급 동시 사용 시 Supabase Realtime 한도와 비용 |
